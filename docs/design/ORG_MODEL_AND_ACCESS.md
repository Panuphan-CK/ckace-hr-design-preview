# โครงสร้างองค์กรและสิทธิ์ของ CKACE (ออกแบบจากข้อมูลที่ Owner ให้ 2026-10-15)

## 1) ข้อเท็จจริงจาก Owner
1. ธุรกิจ: สำนักงานบัญชี (ทำบัญชี) และสำนักงานสอบบัญชี เป็น **2 บริษัทแยกกัน** มี SuperAdmin 2 คน ดูแลคนละบริษัท
2. Admin: พนักงาน 1 คน (สังกัดบริษัทบัญชี) ดูแลพนักงาน **2 ทีม**
3. SuperUser (หัวหน้าทีม) 2 คน ทีมละ 1 คน ดูแลคนละบริษัท
4. User จำนวนมาก แบ่งเป็น 2 บริษัท
5. User 1 คน (ธุรการ) **ขึ้นตรงกับ Admin เท่านั้น** (ไม่ผ่านหัวหน้าทีม)
6. ระบบลาเป็นส่วนหนึ่งของแพลตฟอร์มที่ต้องเชื่อมกันทั้งหมด: ระบบสำนักงานบัญชี, ระบบสอบบัญชี, ระบบ RPA, ฐานข้อมูลพนักงาน

## 2) การตีความ (แก้ได้ถ้าผิด — ทำเครื่องหมาย ❓ ไว้)
- "ทีม" ใน Production ปัจจุบัน = หน่วยงาน (Agency) เช่น ผู้บริหาร / ทีม A / ทีม B; "บริษัท" ยังไม่มีเป็นชั้นของตัวเองในข้อมูล
- ทีมที่ Admin ดูแล 2 ทีม คือ ทีม A และทีม B; หัวหน้าทีม (SuperUser) แต่ละทีมดูแลทีมของตน ❓ ทีมทั้งสองอยู่คนละบริษัทหรือบริษัทเดียวกัน
  (ข้อ 3 บอก "คนละบริษัท" แต่ข้อ 2 บอก Admin สังกัดบริษัทบัญชีและดูแล 2 ทีม → จึงตีความว่า **Admin ข้ามบริษัทได้**)
- SuperAdmin ทำงานในบริษัทของตน (บริษัทบัญชี = คนที่ 1, บริษัทสอบบัญชี = คนที่ 2); ❓ SuperAdmin เห็นข้อมูลของอีกบริษัทหรือไม่ (ตีความ: ไม่เห็น)
- ธุรการ: อยู่ในทีมใดทีมหนึ่งแต่ "เส้นทางอนุมัติ" ข้ามหัวหน้าทีมไปที่ Admin โดยตรง

## 3) สิ่งที่ Project B มีและขาด (ตรวจจาก `packages/database/prisma/schema.prisma`)
| เรื่อง | ปัจจุบัน | ปัญหากับโจทย์นี้ |
|---|---|---|
| บริษัท | ไม่มี (มีแค่ `Agency`, `Department` แบนราบ) | แยก 2 บริษัทไม่ได้, SuperAdmin ต่อบริษัทไม่ได้ |
| บทบาท | `UserRole` ผูกผู้ใช้กับ Role ทั่วทั้งระบบ ไม่มีขอบเขต | "Admin ของทีม A+B" "SuperAdmin ของบริษัท X" แสดงไม่ได้ |
| สายอนุมัติ | `ApprovalPolicy` ต่อ Agency + ต่อประเภทคำขอ; ขั้น = Role + ขอบเขต (SAME_AGENCY/SAME_DEPARTMENT/GLOBAL) | ดีกว่า Production (แยกประเภทได้แล้ว) แต่ไม่มี "ขึ้นตรงต่อ Admin" ต่อบุคคล และ GLOBAL กว้างเกินเมื่อมี 2 บริษัท |
| ผู้บังคับบัญชา | ไม่มี (`managerId`) | ธุรการขึ้นตรง Admin กำหนดไม่ได้ |
| ข้ามระบบ | ไม่มีสัญญา/เหตุการณ์ | ระบบบัญชี สอบบัญชี RPA ต้องรู้ตัวตน/สังกัดของพนักงาน |

## 4) แบบจำลองที่เสนอ (เพิ่มจากของเดิม ไม่รื้อ)
```
Company (บริษัท)              -- ใหม่: นิติบุคคล เช่น สำนักงานบัญชี, สำนักงานสอบบัญชี
  └── Team (= Agency เดิม)     -- มี companyId
        └── Department (ฝ่าย)  -- คงเดิม (ถ้าใช้)
Employee
  ├── companyId (ต้นสังกัดตามสัญญา), teamId (Agency), departmentId
  ├── managerEmployeeId       -- ใหม่: หัวหน้าโดยตรง (ธุรการ → Admin)
  └── employmentState (ACTIVE/PENDING/RESIGNED)
RoleAssignment (แทน UserRole)  -- เพิ่มขอบเขต
  ├── userAccountId, roleId
  └── scopeType: SELF | TEAM_SET | COMPANY | PLATFORM   scopeIds[]
```
ตัวอย่างตามจริง:
| คน | Role | scope |
|---|---|---|
| SuperAdmin บริษัทบัญชี | SuperAdmin | COMPANY(บัญชี) |
| SuperAdmin บริษัทสอบบัญชี | SuperAdmin | COMPANY(สอบบัญชี) |
| Admin | Admin | TEAM_SET(ทีม A, ทีม B) (ข้ามบริษัทได้ ถ้าทั้งสองทีมอยู่คนละบริษัท) |
| หัวหน้าทีม A / B | SuperUser | TEAM_SET(ทีมตน) |
| User ทั่วไป | User | SELF |
| ธุรการ | User | SELF + `managerEmployeeId = Admin` |

### 4.1 การหาผู้อนุมัติ (ตัวคำนวณเดียว)
นโยบายต่อ (บริษัท/ทีม, ประเภทคำขอ) กำหนดขั้นเป็นลำดับ; แต่ละขั้นเป็นชนิดใดชนิดหนึ่ง:
- `ROLE_IN_SCOPE` (ระดับ + ขอบเขต: ทีมเดียวกัน / ชุดทีมที่ผู้อนุมัติดูแล / บริษัทเดียวกัน)
- `DIRECT_MANAGER` (ใช้ `managerEmployeeId`)
- `NAMED_EMPLOYEE` (ระบุตัวบุคคล เช่น ผู้ตรวจรับพิเศษ)
กฎ: ถ้าผู้ขอมี `managerEmployeeId` และนโยบายเปิด "ขึ้นตรง" ให้เริ่มจาก DIRECT_MANAGER แล้วต่อด้วยขั้นระดับสูงกว่า
(ธุรการ: ข้ามหัวหน้าทีม → Admin → SuperAdmin ของบริษัท); ขั้นที่ไม่มีผู้ที่ใช้งานอยู่ → ข้ามพร้อมบันทึกเหตุผล
(Revise จาก Production); ห้ามอนุมัติของตนเอง; ผู้อนุมัติต้องอยู่ในขอบเขตของผู้ขอเสมอ ไม่ใช้ GLOBAL ข้ามบริษัท

### 4.2 สิทธิ์ข้อมูล (ใครเห็นอะไร)
- User: ของตน; SuperUser: สมาชิกในทีมตน; Admin: สมาชิกทุกทีมใน TEAM_SET; SuperAdmin: ทั้งบริษัทตน; ข้ามบริษัทเฉพาะ PLATFORM
  (เจ้าของ/ผู้ดูแลแพลตฟอร์ม) และต้องบันทึกตรวจสอบ
- ข้อมูลส่วนบุคคลอ่อนไหว (ค่ารักษา ใบรับรองแพทย์ ลายเซ็น) เปิดเฉพาะผู้อนุมัติของคำขอนั้นและเจ้าของข้อมูล

## 5) การเชื่อมทั้งแพลตฟอร์ม (สำนักงานบัญชี, สอบบัญชี, RPA, ฐานข้อมูลพนักงาน)
หลักการ: **ฐานข้อมูลพนักงาน (Project B) เป็นแหล่งความจริงของ "ตัวตน + สังกัด + สถานะ"** ระบบอื่นอ่านจากที่นี่ ไม่เก็บสำเนาแยก
- รหัสพนักงาน UUID เดียวกันทั้งแพลตฟอร์ม + รหัสแสดงผลที่อ่านง่าย; ทุกระบบอ้างด้วย UUID
- การเข้าสู่ระบบครั้งเดียว (SSO) ผ่านโดเมน `hr.ckaceaccount.com` / พอร์ทัลอนาคต `app.ckaceaccount.com`; แต่ละระบบมีสิทธิ์ของตนเอง
  (ตารางสิทธิ์ต่อระบบ) ไม่ใช้ Role ของ HR ปนกัน
- สัญญาข้อมูล (API/เหตุการณ์): `employee.created|updated|resigned`, `team.changed`, `role.assigned` ให้ระบบอื่นสมัครรับ;
  ระบบอื่นเขียนกลับเฉพาะผ่าน API ที่ตกลงกัน
- RPA ใช้บัญชีบริการ (service account) สิทธิ์น้อยที่สุด แยกจากบัญชีพนักงาน ไม่ใช้รหัสผ่านมนุษย์; ทุกการเรียกมี audit log
- ข้อมูลลูกค้า/เอกสารสอบบัญชีอยู่ในระบบของตน ไม่ไหลเข้าฐาน HR (ตรงกับที่ตกลง: client data stays local)
- ขอบเขตบริษัทต้องบังคับใช้ที่ชั้นข้อมูลและ API ของทุกระบบ ไม่ใช่แค่หน้าจอ (Frontend ไม่ใช่ผู้ตัดสินสิทธิ์)

## 6) ผลต่อการย้ายข้อมูลจาก Production
- `Agency` เดิม (ผู้บริหาร, ทีม A, ทีม B) → `Team` และต้องกำหนดว่าแต่ละทีมอยู่ `Company` ใด (ต้องให้ Owner ยืนยัน ❓)
- Role เดิม (User/SuperUser/Admin/SuperAdmin) → `RoleAssignment` พร้อม scope ตามตารางข้อ 4; Admin "Global" ในสายเดิม ต้องแปลงเป็น
  TEAM_SET ที่ระบุทีมชัดเจน (ห้ามแปลงเป็น PLATFORM โดยอัตโนมัติ)
- สร้าง `managerEmployeeId` ให้ธุรการ = Admin; ตรวจกระทบยอดหลังย้ายว่าทุกคนมีเส้นทางอนุมัติครบ

## 7) ลำดับงาน (ไม่กระทบ Production จนกว่าจะอนุมัติ)
1. เพิ่ม `Company`, `companyId` ของ Team/Employee, `managerEmployeeId`, `RoleAssignment` (migration ใน Project B เท่านั้น)
2. ปรับตัวคำนวณผู้อนุมัติ + ทดสอบด้วยตัวอย่างผู้ใช้ 5 แบบข้างบน (หน่วย/รวมเทสต์ครบทุกเส้นทาง)
3. ปรับตัวกรองสิทธิ์ข้อมูลทุก endpoint (ปฏิทิน, รายงาน, อนุมัติ, ผู้ใช้) ให้ใช้ scope
4. หน้าตั้งค่า: บริษัท/ทีม/สายอนุมัติต่อประเภท/ผู้บังคับบัญชา
5. สัญญาเหตุการณ์/API สำหรับระบบอื่น + บัญชีบริการ RPA
6. แผนย้ายข้อมูล + กระทบยอด (ต้องการ Owner อนุมัติก่อนทุกขั้นที่แตะข้อมูลจริง)

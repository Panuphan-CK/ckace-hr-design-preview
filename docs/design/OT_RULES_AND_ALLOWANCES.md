# กฎ OT, เวลาพัก และค่าเบิก OT (ออกแบบจากคำสั่ง Owner 2026-10-15)

## 1) ค่าเริ่มต้นของบริษัท (ตั้งค่าได้ ไม่ฝังในโค้ด)
| รายการ | ค่าเริ่มต้น | ระดับที่แก้ได้ |
|---|---|---|
| เวลาทำงาน | 09:00–17:30 จันทร์–ศุกร์ | แพลตฟอร์ม → บริษัท → ทีม → รายบุคคล (มีวันที่เริ่มมีผล) |
| พักกินข้าวเที่ยง | 12:00–13:00 (ไม่นับเป็นเวลางาน) | เหมือนกัน |

| OT วันทำงาน | เริ่ม 17:30 ได้เลย; พักกินข้าวเย็น 17:30–18:30 หรือ 30 นาที เลือกได้ | ต่อคำขอ |
| OT วันหยุด | เริ่ม–เลิกเวลาใดก็ได้; พักเที่ยง/พักกิจกรรม/พักเย็น เลือกได้ ไม่บังคับ | ต่อคำขอ |

หลักการ: ค่าเริ่มต้นมาจากนโยบายบริษัท แต่ผู้ดูแลตั้งทับรายทีมและรายบุคคลได้ (ตัวอย่างที่ตกลงแล้ว: ธุรการขึ้นตรง Admin)

## 2) เวลาพักใน OT (ทำแล้วในโค้ด 2026-10-15)
- คำขอ OT เลือกเวลาพักได้: `LUNCH` 12:00–13:00, `ACTIVITY` 13:00–14:00, `DINNER` 17:30–18:30, `DINNER_SHORT` 30 นาที
- ไม่เลือก = ไม่หักเวลา; เลือก = หักเฉพาะส่วนที่ซ้อนกับช่วง OT จริง (ไม่หักเกินที่ซ้อน); `DINNER` แทน `DINNER_SHORT`
- ถ้าไม่ส่งรายการพัก (API เก่า/LIFF) ใช้พฤติกรรมเดิม: พักเที่ยงหักเสมอ + พักเย็นหักเฉพาะวันที่ไม่ใช่วันทำงาน
- ไฟล์: `packages/business-rules/src/overtime.ts` (+ เทสต์), สัญญา `OvertimeCreateInput.breaks`, API ผ่านค่า `breaks`, หน้า OT มีปุ่มเลือกพัก
- ยังไม่ทำ: เก็บรายการพักที่เลือกไว้ในฐานข้อมูล (ตอนนี้เก็บเฉพาะนาทีที่คำนวณแล้ว) → ต้องเพิ่มคอลัมน์ `breakCodes` ที่ `overtime_segments` (migration)

## 3) OT ต้องมีการลงเวลาเข้างานปกติ
- ผู้ทำ OT ต้องลงเวลาเข้า-ออกตามปกติ (เหมือน Production: วันหยุดลงเวลาได้เมื่อมี OT ที่อนุมัติ)
- ชั่วโมง OT ที่จ่าย = ส่วนที่ **ทับกันระหว่างช่วงที่อนุมัติกับช่วงที่ลงเวลาจริง** (Production: เริ่มนับจากเวลาเริ่มที่อนุมัติ ถึงเวลาออกจริง ไม่เกินเวลาสิ้นสุดที่อนุมัติ)
- ไม่มีบันทึกลงเวลา → ไม่มีชั่วโมง OT ที่จ่าย (รายงานแสดงสถานะ "ยังไม่ลงเวลา" ไม่ใช่ศูนย์เงียบ ๆ)
- Project B มีโครง `overtime_segments.attendanceRecordId` และการผูกแล้ว; ต้องเพิ่มการคำนวณ "นาทีที่จ่ายจริง" จากการทับกัน

## 4) ค่าเบิกประกอบ OT แบบอัตราคงที่ (FIX RATE) — ใหม่
สองรายการ ตั้งค่าได้: **ค่ารถ (ค่าเดินทาง)** และ **ค่าข้าว OT**
```
OvertimeAllowancePolicy      -- ต่อ บริษัท/ทีม/รายบุคคล + วันที่เริ่มมีผล (ลำดับความสำคัญ: บุคคล > ทีม > บริษัท > ค่าเริ่มต้น)
  kind            TRANSPORT | MEAL
  amount          จำนวนเงินคงที่ต่อสิทธิ์ (บาท)
  perUnit         PER_OT_DAY | PER_REQUEST      -- ❓ จ่ายต่อวัน OT หรือต่อใบคำขอ (เริ่มต้น: ต่อวัน OT)
  dayType         ANY | WORKDAY | HOLIDAY       -- ❓ จ่ายทุกวันหรือเฉพาะวันหยุด/วันทำงาน
  minPayableMinutes  เกณฑ์ขั้นต่ำของชั่วโมง OT ที่จ่ายจริง (ค่าเริ่มต้น 0 = ไม่มีเกณฑ์) ❓เช่น ≥ 2 ชม. ถึงได้ค่าข้าว
  startsAfter     เวลา OT ต้องเลยจากเวลานี้ (เช่น 20:00 สำหรับค่ารถ) หรือว่าง ❓
  active, effectiveFrom, effectiveTo
OvertimeAllowanceLine        -- ผลคำนวณต่อ OT segment เมื่ออนุมัติ+มีการลงเวลา
  segmentId, kind, amount, policySnapshot (เก็บค่าที่ใช้คำนวณ ณ ตอนนั้น)
```
กฎสำคัญ: ใช้สัญญาเงินแบบ **สแนปช็อต** (ไม่คำนวณย้อนหลังเมื่อปรับอัตรา); สิทธิ์ค่าเบิกเกิดเมื่อคำขอ OT **อนุมัติ + มีการลงเวลาจริงตามเงื่อนไข**;
ยกเลิก/ถอน OT → รายการค่าเบิกถูกกลับรายการ (reversal) ไม่ลบทิ้ง; อัตราเริ่มต้นเป็น 0 บาท จนกว่า Owner ตั้งค่า (ระบบไม่เดาตัวเลข)

## 5) รายงาน OT ออกเป็น Excel (.xlsx)
- ตัวกรอง: ช่วงวันที่, บริษัท, ทีม, พนักงาน, สถานะ; สิทธิ์ตามขอบเขตของผู้ดู (ผู้ดูแลทีมเห็นเฉพาะทีมตน)
- คอลัมน์: รหัสคำขอ/วันที่/พนักงาน/ทีม/บริษัท/เวลาเริ่ม–สิ้นสุดที่อนุมัติ/เวลาเข้า–ออกจริง/นาทีที่ขอ/นาทีที่จ่ายจริง/พักที่ใช้/
  ประเภทวัน (ทำงาน/หยุด)/สถานะ/ค่ารถ/ค่าข้าว/รวมเงิน; แถวสรุปรายบุคคลและรวมทั้งหมด; ชีตที่สองเป็นสรุปต่อบุคคล
- ป้องกัน CSV/Excel injection (ขึ้นต้นด้วย = + - @ ใส่เครื่องหมายนำหน้า) เหมือนที่ใช้ใน CSV เดิม; ไม่แนบข้อมูลเกินสิทธิ์ผู้ดู;
  บันทึก audit ทุกครั้งที่ส่งออก (ใคร/ช่วงไหน/กี่แถว)
- ใช้ไลบรารีเขียน .xlsx ฝั่งเซิร์ฟเวอร์ (ต้องเพิ่ม dependency — ตรวจ/ล็อกเวอร์ชันก่อน)

## 9) ผู้อนุมัติระดับ SuperAdmin ระหว่างสองบริษัท (Owner 2026-10-15 16:02)
- SuperAdmin ทั้งสองคน **เห็นข้อมูลของกันและกัน** (อ่านได้ข้ามบริษัท)
- **อนุมัติ/แก้ได้เฉพาะของบริษัทตน** (สิทธิ์เขียนผูกกับบริษัท ไม่ใช่การมองเห็น)
- **แจ้งเตือนส่งไปที่ SuperAdmin อีกคนเท่านั้น** ตีความ: คำขอที่ SuperAdmin ยื่นเอง ถูกส่งเข้าคิวและแจ้งเตือนเฉพาะ SuperAdmin อีกคน (อนุมัติไขว้กัน)
  ❓ ถ้าหมายถึงอย่างอื่น (เช่น เหตุการณ์ของบริษัท A แจ้ง SuperAdmin ของ B เท่านั้น) บอกได้ — ทำเป็นค่าตั้งได้ทั้งสองแบบ
- ผลต่อแบบจำลองสิทธิ์: แยก `readScope` กับ `approveScope` ใน `RoleAssignment` (อ่านทั้งแพลตฟอร์ม / เขียน-อนุมัติเฉพาะบริษัท) และขั้นอนุมัติแบบ `PEER_AT_SAME_LEVEL`

### 10.1 สายอนุมัติมี 3 อัลกอริทึมที่ต่างกัน (ไม่ใช่ชุดเดียวใช้ร่วมทุกประเภท)
| ประเภท | วิธีหาผู้อนุมัติ | หมายเหตุ |
|---|---|---|
| ลา, OT | รายชื่อผู้ใช้ตามระดับ+ขอบเขตของหน่วยงาน ผู้ขอเลือกเอง 1 คนต่อระดับ | OT ถ้าไม่ส่งรายชื่อมา ระบบใช้ **ทุกคนในรายชื่อ** เป็นขั้นต่อกัน |
| ค่ารักษา | **ระบบเลือกให้** คนแรกที่เจอของแต่ละขั้น; **ตัดขั้นระดับ SuperAdmin ออก**; ผู้ขอระดับ SuperUser เริ่มหลังขั้น SuperUser; Admin/SuperAdmin อนุมัติอัตโนมัติ | ขอบเขต SuperUser ในสังกัดต้องตรงทั้งหน่วยงานและฝ่าย |

ข้อเสนอ: ใช้ตัวคำนวณสายเดียว กำหนดนโยบายต่อประเภท (ใครเลือก/ระบบเลือก/ขั้นสูงสุด) ในหน้าตั้งค่า; ทุกประเภทแสดงชื่อสายก่อนส่ง; ผู้ขอระดับสูงต้องยื่นแก้ไขเวลาได้ (ผ่านผู้อนุมัติระดับถัดไป)

### 10.2 การอนุมัติและสิทธิ์เห็นข้อมูล (`02_Approval.js`, `23_ApprovalSecurity.js`)
- ต้องอนุมัติเรียงขั้น: ขั้น N ทำได้เมื่อขั้นก่อนหน้า Approved ทั้งหมดและขั้นหลัง Pending ทั้งหมด; ขั้นสุดท้ายอนุมัติ = Approved; ใครไม่อนุมัติ = Rejected ทันที (ต้องมีเหตุผล, ความเห็น ≤ 1000)
- ลา: อนุมัติครั้งสุดท้ายแล้วสร้างเหตุการณ์ใน Google Calendar กลาง (ID ในชีต Setting, ทำแบบ best-effort); OT ทำเหมือนกัน
- Session: ลายเซ็น HMAC อายุ 1 ชั่วโมง ผูกกับแฮชรหัสผ่าน (เปลี่ยนรหัสแล้ว session เดิมใช้ไม่ได้)
- ขอบเขตการเห็น: SuperAdmin เห็นทั้งหมด; Admin ที่หน่วยงานตนตั้งสายเป็น "Admin ทุกสังกัด" เห็นทั้งหมด ไม่ใช่เห็นเฉพาะหน่วยงาน; Admin อื่น = หน่วยงานเดียวกัน; SuperUser = หน่วยงานและฝ่ายเดียวกัน; User = ของตน
- ไฟล์แนบค่ารักษาถูกซ่อน URL สำหรับผู้อ่านที่เป็นผู้ดูแลระดับสูง (ต้องดาวน์โหลดผ่านฟังก์ชันที่ตรวจสิทธิ์)

### 10.3 ผู้ใช้ (`06_Users.js`, `24_UserManagementSecurity.js`, `09_UserPolicies.js`)
- สมัคร: ชื่อผู้ใช้ไม่ซ้ำ, รหัสผ่านอย่างน้อย 6 ตัว, สร้างเป็น Role `User` สถานะยังไม่ใช้งาน; ยังไม่สร้างสิทธิ์ลา

## 11) การแจ้งเตือน อีเมล LINE และปฏิทิน (อ่านจาก `00_Notification.js`, `16_sendPushMessage.js`, `15_Calendar.js`, `18_Overtime.js`, `02_Approval.js`)

### 11.1 ใครได้รับอะไรผ่านช่องทางไหน
| เหตุการณ์ | อีเมล (Gmail ของเจ้าของสคริปต์) | LINE push |
|---|---|---|
| ยื่นคำขอลา | ผู้ขอ (ทุกครั้งที่สถานะเปลี่ยน รวมตอนยื่น) + ผู้อนุมัติ **ขั้นที่ถึงคิว** | ผู้อนุมัติขั้นที่ถึงคิว (priority normal); ผู้ขอได้ LINE เมื่อสถานะไม่ใช่ Pending (priority critical) |
| อนุมัติ/ไม่อนุมัติ/ส่งกลับ (ลา) | ผู้ขอ + ผู้อนุมัติถัดไป (ถ้ายัง Pending) | ผู้ขอ (critical) + ผู้อนุมัติถัดไป |
| แก้ไขเวลา | ไม่มี | ผู้อนุมัติ (normal), ผู้ขอเมื่อมีผล (critical) |
| OT | ไม่มี | ผู้อนุมัติ (normal), ผู้ขอเมื่อมีผล (critical), มีแบบรวมกลุ่มหลังอนุมัติหลายรายการ |
| ค่ารักษา | ไม่มี | ผู้อนุมัติ (normal), ผู้ขอเมื่อมีผล (critical) |
| สมัครสมาชิกใหม่ | ไม่มี | **LINE ID ของบุคคลเดียวที่ฝังในโค้ด** (ไม่ใช่ผู้ดูแลทุกคน) |
| ผู้ใช้ได้รับอนุมัติ | อีเมลเฉพาะเมื่อผู้ใช้ยังไม่ผูก LINE | LINE (critical) มีสำรองเป็นอีเมล |
| เตือนงานค้าง > 24 ชม. | ไม่มี | ผู้อนุมัติขั้นแรกที่ค้าง (low) วันละครั้งต่อรายการ |
- ข้อสังเกต: ประเภท แก้ไขเวลา/OT/ค่ารักษา ส่งอีเมลไม่ได้เลย ถ้าผู้ใช้ไม่ผูก LINE จะไม่ได้รับแจ้ง; ผู้ใช้ที่ไม่มี LINE ID ไม่ได้ LINE
- ไม่มีการแจ้งฝ่ายบุคคล/ผู้ดูแลเมื่ออนุมัติขั้นสุดท้าย ไม่มีสรุปรายวัน ไม่มีการเลือกช่องทางต่อผู้ใช้
- ส่งหลัง commit แบบ best-effort ถ้าล้มเหลวไม่ย้อนข้อมูล (แต่ไม่มีคิวส่งซ้ำ ยกเว้น LINE ที่ log ลงชีต `LineMessageLog`)

### 11.2 นโยบายโควตา LINE (ฟรีมีจำกัดต่อเดือน)
- อ่านโควตา/การใช้งานจาก LINE API (cache 5 นาที); ≥ 85% หยุด priority `low` (เตือนค้าง); ≥ 95% ส่งเฉพาะ `critical`; ครบโควตา หยุดทั้งหมด
- กันซ้ำด้วย dedupe key ใน cache (ค่าเริ่มต้น 10 นาที สูงสุด 6 ชม.); อีเมลสำรองใช้เฉพาะเมื่อกำหนด `emailFallback` และไม่ใช่ low
- Reply ตอบผู้ใช้ที่เริ่มบทสนทนาไม่นับโควตา

### 11.3 ปฏิทิน (Google Calendar กลางของผู้บริหาร)
- สร้าง Event เมื่อ **ลา** อนุมัติขั้นสุดท้าย (เต็มวัน ชื่อ "ลา: ชื่อ (ประเภท)" รายละเอียดมีเหตุผล+รหัสคำขอ) และเมื่อ **OT** อนุมัติ (ตามช่วงเวลา ชื่อ "OT: ชื่อ" ไม่มีรายละเอียด)
- ไม่มี Event ให้ แก้ไขเวลา/ค่ารักษา; ไม่มีปฏิทินส่วนตัวของพนักงาน

- ผลต่อ Project B: ปฏิทินในแอปคือแหล่งความจริง; ถ้าต้องส่งออกไป Google/Outlook ให้ทำเป็นฟีด ICS หรือการซิงก์ที่รองรับ แก้/ลบ และอย่าฝังรหัสปฏิทินในโค้ด

- **สำรองแบบ "เรียลไทม์": ทุกครั้งที่มีการแก้ไขชีต สคริปต์คัดลอกไฟล์ทั้งไฟล์หนึ่งชุด** แล้วลบสำเนาที่เก่ากว่า 2 วันทุกวัน → ย้อนกลับได้จริงแค่ 2 วัน
  และเปลืองโควตา Drive; ไฟล์สำรองประจำปีสร้างเดือนธันวาคมเท่านั้น
- ใช้ LockService ระดับสคริปต์ (หนึ่งงานเขียนต่อครั้งทั้งระบบ รอล็อก 5–30 วินาที ถ้าไม่ได้ตอบว่ากำลังดำเนินการ)
- Idempotency ใช้ CacheService 6 ชม. (ไม่ถาวร); ธุรกรรมข้ามหลายชีตไม่เป็น atomic ใช้การไล่ลบแถวที่สร้างค้างเมื่อพัง
- Project B: ฐานข้อมูลเชิงสัมพันธ์ + ธุรกรรม + สำรองรายวัน/PITR จึงแก้ได้ทั้งหมด แต่ต้องมีแผนย้ายและตรวจกระทบยอด

### 12.6 หน้าเว็บ (page/*.html)
- ตรวจฟอร์มส่วนใหญ่ฝั่งไคลเอนต์ (เหตุผลไม่อนุมัติต้องกรอก, ต้องมีผู้อนุมัติ ≥ 1, ต้องแนบใบเสร็จ, ต้องเลือกช่วงเวลา, โควตาไม่เกิน)
